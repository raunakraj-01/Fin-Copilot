# Hisaab new features: implementation plan

Source: [`NEW_FEATURE.md`](NEW_FEATURE.md). This is an implementation plan for the current repository, not a claim that the four features already exist. Build in the order below; each phase has an independently testable result. All money is integer paise and all business dates are validated `YYYY-MM-DD` dates.

## Current baseline and shared prerequisites

The app uses React 19, Vite 7, Recharts 3, Express 4, Zod 4, Mongoose 8/MongoDB, and Vitest. `CashItem` holds receivables/payables and outstanding amounts; `buildForecast` in `server/src/services/finance/forecast.js` computes the 90-day cash curve. `analyzeNewOrder` and `analyzeRescue` are pure simulations. Imports use `normalizeRows`; imported `externalId` is unique per workspace, category, and source system. The app is currently a synthetic, unauthenticated demo. Do not enable external sync, pooled telemetry, messages, payments, or bank exports for real businesses until tenant authentication, workspace authorization, consent, encryption, retention, and audit controls exist.

First add a tenant/user identity and workspace membership check to every existing and new `/api/workspaces/:workspaceId/*` route. Bind background device credentials and webhook accounts to that membership. Add an append-only event/audit collection with actor, workspace, action, idempotency key, timestamp, source reference and result; redact bank identifiers, phone numbers, and message bodies from routine logs. Keep existing demo mode isolated. Use server-side rate limits and a secret manager for Tally bridge credentials, WhatsApp and payment provider secrets. Do not let an AI response authorize a write or payment.

## 1. Local Tally bridge and automatic deltas

**Stack:** Small Go Windows service plus optional tray status UI; Go standard `net/http`, `encoding/xml`, `crypto/hmac`, `crypto/sha256`, SQLite for the local outbox/checkpoint, Windows service/task scheduler, HTTPS/TLS 1.3 to the existing Express API. Keep the cloud importer in Node/Mongoose/Zod. Start with TallyPrime XML over localhost port 9000; ODBC 5656 is a later compatibility adapter only if a tested Tally version requires it. Tally documents XML-over-HTTP and the default port [here](https://help.tallysolutions.com/xml-integration/) and the need for a running company/server [here](https://help.tallysolutions.com/pre-requisites-for-integrations/).

**Method:** Pair a device to one workspace using a short-lived enrollment token. The service probes `127.0.0.1:9000`, then sends a read-only `Export Data` XML envelope for a scoped voucher/ledger report. Confirm the exact report and field names against a real TallyPrime export before coding the parser. Select company GUID; extract voucher GUID/master ID, alteration ID, dates, party, invoice reference, amount, settlement and cancellation state. Never POST an import or alteration command to Tally. Poll nightly and on startup; use bounded timeouts, exponential backoff and an encrypted local outbox for offline periods. Avoid relying only on a last-modified timestamp: query an overlap window and periodically reconcile the full active ledger, because backdated edits/deletions can invalidate a simple watermark.

**Delta identity:** `sourceKey = (workspaceId, companyGuid, voucherGuid, lineId)`; `version = alterationId` when available, otherwise a canonical content digest. Ignore an identical version, upsert a changed version, and tombstone a deleted/cancelled source entry. Record `lastSuccessfulSync` only after the server acknowledges the entire batch. A stable batch id and per-row idempotency key make retries safe. Validate every row with a Tally-specific adapter, then reuse `normalizeRows`/`CashItem` rules where possible. Extend `CashItem` provenance rather than squeezing a multi-line voucher into the existing `externalId` alone. Recompute the workspace cash snapshot only from an explicit bank/cash balance feed; never add historical vouchers to opening cash and count them again as forecast events.

**Privacy:** Keep raw PAN/GSTIN on the device unless the user separately opts into the network feature. Plain salted SHA-256 is vulnerable to guessing from the small GSTIN namespace; use an HMAC-SHA-256 keyed pseudonym for exact matching, with centrally managed rotation/versioning and explicit consent. Transport only required deltas, not the entire ledger. Add `POST /api/workspaces/:id/sync/batches`, `GET /sync/status`, device revocation, and a Setup status card showing last sync, count and errors. Acceptance: edits, partial settlements, deletions, backdated entries, offline retries and duplicate batches yield exactly one correct ledger state; the forecast changes only after a committed sync.

## 2. GSTIN-level DSO Truth Score

**Stack:** Existing MongoDB/Mongoose aggregation and pure Node functions; no new analytics service initially. Add a private `PaymentObservation` collection separated from user-facing `CashItem`. Add an opt-in consent record and deletion/withdrawal path. Use HMAC pseudonyms for both buyer identity and contributing supplier identity. Keep the secret out of the database and client.

**Input requirements:** Actual invoice issue/acceptance date, agreed due date, each cleared payment date and paise amount, verified payment source, and reversals. Current `CashItem` has due/expected dates and `settledPaise` but not payment timestamps; do not infer realized DSO from forecast dates or `updatedAt`. Add settlement events from verified bank/payment reconciliation or confirmed Tally entries before scoring.

**Formulas:** For each fully paid invoice, `daysToClear = clearedDate − invoiceDate` in UTC calendar days; `daysLate = max(0, clearedDate − agreedDueDate)`. For partial payments, compute `weightedClearDays = Σ(paymentPaise × daysFromInvoiceToPayment) / Σ(paymentPaise)` using `BigInt` intermediates and a documented integer rounding rule. Publish separately the integer median clearance days, median lateness days, sample invoice count, and distinct supplier count over a defined rolling window (for example 12 months). `DSO Truth Score` should be a named, versioned transform of observed lateness, not an unexplained 0–100 claim; propose `score = clamp(0, 100, 100 − 2 × medianLatenessDays)` for product review and do not expose it until calibrated on consented data. Always display sample size and window.

**Privacy gate:** The source says `k ≥ 5`; require at least five distinct, independent supplier tenants with meaningful verified observations before returning any buyer aggregate. Suppress narrow filters, small cells, and combinations that can reveal a supplier by subtraction. Define one supplier contribution cap and a minimum invoice count; test collusion and deletion effects. No supplier names, invoice IDs, or row-level outcomes leave the tenant. A new `GET /api/workspaces/:id/counterparties/:id/reliability` returns only eligible aggregates. For an order analysis, compare the contractual final payment date with `orderDate + observedMedianClearDays`; run `analyzeNewOrder` twice using the same costs/advance, once per date. Label the network scenario conditional, never silently replace the entered date. Acceptance: below-threshold data yields no score; five independent suppliers unlock only aggregates; correction/withdrawal updates them; the baseline simulation remains unchanged.

## 3. WhatsApp acceleration and payment settlement loop

**Stack:** Existing Rescue Planner/React, Express/Zod/Mongoose, Meta WhatsApp Cloud API, and one contracted payment gateway (Razorpay or Cashfree) with UPI/net-banking payment links and signed webhooks. Pick the provider after checking current API, settlement and fee terms. Add `CollectionOffer`, `OutboundMessage`, `PaymentAttempt`, and `SettlementEvent` records, each with unique provider/idempotency IDs. Phone number and buyer consent are mandatory; use approved WhatsApp templates where the provider requires them.

**Method:** From an eligible `accelerate_collection` candidate, show an owner-reviewed preview containing invoice, original outstanding, proposed early date, discount, net amount, fees, and forecast effect. The owner explicitly sends the offer. Create a short-lived payment link bound to the offer and amount, then submit the approved message once. Track delivery and offer expiry. A link click or message delivery never marks an invoice paid. Verify the payment webhook signature against the raw request body, deduplicate provider event IDs, confirm paid status/amount/currency/reference server-to-server, and append a settlement event in a transaction. Update only the correct invoice's `settledPaise`/status, then recompute forecast. Handle partial payments, expiry, refunds and chargebacks by compensating events; never overwrite history.

**Formulas:** For outstanding `P` paise and discount `b` basis points (2% = 200), `discountPaise = roundHalfUp(P × b / 10_000)` with `BigInt`; `buyerPaysPaise = P − discountPaise`. If the platform fee is 0.25% (25 basis points), compute `feePaise = roundHalfUp(buyerPaysPaise × 25 / 10_000)` only when the commercial agreement actually charges it; `netCashPaise = buyerPaysPaise − gatewayFeePaise − platformFeePaise`. Model the net receipt on the offered clearance date and all fees on their actual debit dates using `buildForecast`/rescue additional events. Never treat an offer as a confirmed receipt before verified payment. Show whether the fee is borne by seller or buyer and reject ambiguous configurations. Use checked safe-integer conversions at the persistence boundary.

**Interfaces and checks:** Add offer preview/create/send/status routes under the workspace, a dedicated signed provider webhook route, and a Rescue Planner action with a visible audit trail. Tests cover exact paise rounding, webhook forgery, duplicate/out-of-order events, partial payment, refunds, double-click send, wrong workspace, expired offers and forecast recomputation. Launch behind a per-workspace feature flag and provider sandbox, then a low-value pilot. Do not assert a 0.25% take-rate is legally or commercially available until provider terms are confirmed.

## 4. Bank-ready working-capital dossier

**Stack:** Existing React/Express/Mongoose/forecast engine plus a server-side PDF renderer already used by the project if available, otherwise a single maintained PDF library. Render server-side and provide a versioned PDF plus machine-readable calculation JSON. Keep raw source values and sign-off fields in a `DossierSnapshot` with as-of date, source IDs, template version and generation timestamp.

**Inputs:** Reconciled cash/bank balances; receivable issue/due/cleared dates; inventory and creditors; audited financial statements and sales projections; CC/OD limit, bank template and sanction terms; verified MSME status, acceptance date, written agreement and payments for Section 43B(h). The current models do not contain most of these. Add explicit input/reconciliation screens, provenance and completeness checks. Missing fields produce a marked draft, not a bank-ready certificate.

**Calculations:** Use `buildForecast` for the 90-day cash budget: `closingCash[d] = openingCash + cumulativeReceipts[d] − cumulativePayments[d]`, and display reserve breaches. Debtor aging at as-of date uses `ageDays = max(0, asOfDate − invoiceDueDate)` for overdue buckets `0–30`, `31–60`, `61–90`, `91–180`, `>180`; also show invoice-age buckets separately if a bank template asks for them. `outstandingPaise = amountPaise − settledPaise`, exclude cancelled/fully settled records, and reconcile bucket totals to receivable control totals. For any requested MPBF/Tandon-style illustration, show the chosen bank's documented method and formula/version in the report; do not present it as a universal current RBI requirement. RBI material says the earlier prescribed MPBF method was withdrawn [here](https://www.rbi.org.in/commonman/Upload/English/Notification/PDFs/84MGI010709_F.pdf). Section 43B(h) status needs verified micro/small classification and the MSMED Act timing inputs; an Income Tax Department explanation is [here](https://www.incometax.gov.in/iec/foportal/sites/default/files/2024-09/Webinar%20PPT%20for%203CA-3CD_3CB-3CD_13.09.2024.pdf). Have a CA and the target bank approve the template and statutory interpretation before calling the output compliant.

**Output and checks:** Add `POST /api/workspaces/:id/dossiers/preview` (completeness and calculations) and `POST /dossiers` (immutable generated snapshot); UI offers review, source drill-down and export. Header states bank, template, accounting period, assumptions, data freshness and draft/verified status. Tests reconcile every PDF figure to calculation JSON, confirm missing-data refusal of a certification claim, verify aging boundaries (90/180), partial settlements, negative cash and historical snapshot immutability. Validate printed A4 pages visually.

## Delivery order and release gates

1. Tenant security, consent, audit and reconciliation foundations; preserve current demo behavior and test the existing API routes.
2. Tally bridge pilot with one tested TallyPrime version/company and an idempotent server sync. Measure daily success, lag and correction rate.
3. Verified settlement events and private DSO aggregation; launch network output only after consent and anonymity review.
4. Offer preview, provider sandbox, signed webhook and settlement reconciliation; require owner approval for each send.
5. Dossier input completeness, bank-specific template, CA review and PDF export.

At every phase run `npm --prefix server test`, `npm --prefix client run build`, focused integration tests, and data-isolation tests across two workspaces. Run deployment and provider sandbox tests before a live pilot. Roll out per tenant with a kill switch and observe sync failures, duplicate events, webhook reconciliation and export errors. Claims in `NEW_FEATURE.md` about market size, typical CA fees, bank acceptance, payment timing and conversion are product hypotheses until measured or verified with a bank/provider.
